## 六年，从服务端到模型

我是大梁，英文名 Archibald，在深圳。2017 年注册 GitHub，六年时间基本都花在「把一个东西从能跑到能上线」这件事上。

起点在服务端：Java / Spring 的服务、PostgreSQL 的数据、MyBatis 的持久层、Dubbo 的服务化。这段经历给我的不是某个框架的熟练度，而是一种习惯 —— 先把数据的形状想清楚，再想接口和界面。表结构错了，上面的代码写得多漂亮都没用。

后来往前端走。不是为了「全栈」这个标签，而是因为发现界面上的问题经常不能靠改界面解决：筛选器卡，是因为数据没在正确的地方聚合；页面慢，是因为一开始没把渲染边界划对。自己写一遍，才知道该往前端提什么样的需求。

## 现在：AI Native

近两年我的重心转到了 AI 上，但我对「AI Native」的理解可能和流行的说法不太一样。

我不太相信「接一个大模型 API 就叫做 AI 产品」。真把 LLM 放进工程里，麻烦的是别的部分：输出的不稳定性怎么兜住、外部依赖挂了怎么降级、生成的东西怎么验证、成本怎么控制、以及最关键的 —— 这个功能到底替用户省掉了什么。

所以我的项目基本都是围绕这些问题在做的：

- **Silicon River** 里，我用了三个榜单交叉验证再加一层联网检索，因为单一榜单会被模型厂商的发布策略带跑，而 LLM 单靠自己又会一本正经地编
- **Idea Probe** 里，我坚持把输出拆成 claim 和 evidence，而不是给一段摘要 —— 摘要不可比对，claim 可以

## 我是怎么工作的

- **先写清楚再动手**。Idea Probe 是先写 PRD 才开始写代码的，PRD 里还专门有一节「现实校准」，把理想和这一版真能做的分开。这节省的时间远超写文档的成本。
- **降级优先**。任何依赖外部服务的系统，先想清楚它挂掉之后会怎样，再想正常路径。
- **测试是给未来的自己看的**。Silicon River 的 75+ 测试用例里，最有用的那些是在改数据源之后帮我确认没改坏别的东西的。
- **不确定就说不确定**。这一点写在代码注释和 commit message 里，也写在这里。
